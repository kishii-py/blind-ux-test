# シナリオパターン集 — ゴール文の型

ゴール設計時はここから選び、自分のシステムのデータに合わせて具体化する。
各パターンは「**何を測るか**」が異なる。1 回の監査で 2〜3 パターンを組み合わせると効率がよい。

すべて実走で有効性を確認済み（7 システム・延べ 45 走行）。「実績」は、そのパターンが
実際に何を検出したかの記録。

---

## A. 作成一本道 (create-flow)

- **ゴール型**: 「◯◯から △△ を N 個、納期 X で注文を受けた。登録して」
- **測るもの**: 主業務フローの導線・必須項目の分かりやすさ・既定値の親切さ
- **実績**: 金額 0 のまま登録できてしまう問題を検出 / 日付カレンダーの見切れを検出
- **注意**: 達成の DB 裏取り必須（登録**内容の正確性**まで見る。「登録できた」だけでは不十分）

## B. 調べ物 (lookup)

- **ゴール型**: 「上司に ◯◯ の状況と数字を聞かれた。調べて答えて」
- **測るもの**: 検索・一覧・集計の発見可能性。**答えの正確性（誤答 = 最重要所見）**
- **実績**: メニュー総当たりでしか到達できない画面を検出 / KPI 数値がドリルダウンできず
  内訳に辿り着けない問題を検出

## C. ロック解除・状態遷移 (guarded-edit)

- **ゴール型**: 「承認済み / 確定済みの ◯◯ を修正することになった。直せる状態にして」
- **測るもの**: ガード UI の案内力（エラーメッセージが**次の行動**を教えるか）
- **実績**: 12 手 / 詰まり 0 で完遂 — 褒め所見の代表例。良い設計の確認にも使える

## D. マスター修正 (master-edit)

- **ゴール型**: 「◯◯ の登録値が実物と違っていた。正しくは X。直して」
- **測るもの**: 一覧からの編集導線（右クリック等の**隠れ導線**の発見可能性）
- **実績**: 経験者ペルソナは右クリックを発見できたが、「前職と比べて違和感がある」と記録した

## E. 公開・共有 (publish)

- **ゴール型**: 「◯◯ を社外の協力会社にも見られるようにして」
  （URL は「コピーボタンを押した」等の**操作の記録**でよい。長い文字列の転記をゴールにしない）
- **測るもの**: トグル系設定の意味の分かりやすさ・完了状態の確認可能性
- **実績**: トグルの説明文が優秀であることを 3 ペルソナで確認

## F. 整理・個人化 (organize)

- **ゴール型**: 「◯◯ をあとで自分がすぐ開けるようにして」
- **測るもの**: ブックマーク・お気に入り等の個人化機能の発見可能性
- **実績**: ボタンと一覧が対になっている設計で全員が即到達

## G. 削除ガード (protected-delete) — 高収穫

- **ゴール型**: 「整理対象になった ◯◯ をマスターから削除して。**できない場合は、画面が
  『なぜ・どうすれば』を教えてくれたかを報告して**」
  （**参照が多いデータを選ぶ**。「できなかった報告も完了」と明記すると、不可能タスクを
  正当に扱える）
- **測るもの**: 削除ガードのメッセージが理由と対処を教えるか / **失敗フィードバックの知覚可能性**
- **実績**: 「押しても何も起きない・何も言わない削除」（重大バグ候補）を 2 ペルソナで検出。
  正解キー = 対象レコードの**存在**（削除されて**いない**ことも裏取りする）

## H. 複数画面往復 (multi-screen)

- **ゴール型**: 「在庫を確認して、少ないようなら N 発注して」
  （**判断を含むゴール**も成立する — 在庫 12.4kg を「少ない」と正しく判断して発注まで完遂した実績）
- **測るもの**: 画面間の文脈引き継ぎ（確認した品番・仕入先が発注画面に自動反映されるか）/
  **操作後の再描画**（確定後に一覧が自動更新されるか）
- **実績**: 引き継ぎは良好だったが、確定後の一覧がリロードしないと更新されない問題を検出
- **コツ**: 指示に「画面間の引き継ぎを必ず記録」の専用項目を入れると測定が安定する

## I. 検索・フィルタ (search-filter)

- **ゴール型**: 「6 月に ◯◯ へ出荷した分は何件か」
  （**単位を添えさせる**: どの一覧で・何を単位に数えたか）
- **測るもの**: 期間 + 条件の組み合わせ絞り込みの操作性・集計値の信頼性
- **実績**: サマリーカード / 明細行数 / 得意先別集計の 3 箇所が一致していたため
  「自信を持って答えられた」— 集計画面の**良かった点**として記録価値あり

## J. 既存システムとの比較 (canon-baseline)

- **ゴール型**: 自社の**別システム（正典・お手本にしたい方）**の同種画面に、同じゴール型を走らせる
- **測るもの**: 「これは複雑すぎるのか、そもそもこの業務が複雑なのか」の切り分け基準値
- **実績**: 調べ物系ゴールで 新人 26 手 / 経験者 34 手 / 詰まり各 1。同型ゴールの別システムは
  経験者 21 手 — 移植による操作感の劣化は数字上検出されなかった
- **注意**: **正典でも所見は出る**（正典 ≠ 完成品として扱う）

## K. 狭幅ビューポート (mobile/tablet)

- **ゴール型**: 通常幅の腕と**同一のゴール文**を、狭幅（820×1180 = タブレット縦）の腕に走らせる
- **追加指示は 1 段だけ**: 「開始前に `browser_resize` で 820×1180 にする。**以後 resize 禁止**
  （狭くて見えない場合もスクロールで対処）」
- **測るもの**: **「同一の壁に両腕が当たれば幅非依存の構造問題」の切り分け** ← 本パターンの最大価値
- **実績**: 4 システムで対比が成立。狭幅固有の典型 = ハンバーガー再展開が遷移ごとに +1 手 /
  リストボックス内部スクロールの先頭隠れ / 多列テーブルの横スクロール往復
- **幅誘発という第 3 分類**: 全幅共通の構造欠陥（機能していないパンくずリンク等）が、
  狭幅の「戻る導線探し」で初めて露出することがある。**幅固有 / 幅誘発 / 幅非依存**の
  3 分類で回収する

## L. エラーリカバリ (error-recovery)

- **明示設計が正**: ゴール文に「まず ◯◯ を入れずに保存を試してから、画面の指示に従って
  直して完成させて。エラー表示が『何をどう直すべきか』を教えてくれたかを必ず報告して」を埋め込む
  （**自然発生待ちは不発**の実測 — ペルソナは賢く必須項目を埋めてしまう）
- **測るもの**: エラー表示の形式（インライン / トースト、逐次 or 全件、残留性）・
  **欄マーキングの有無**・文言の案内力・回復までの手数・回復中の不安記述
- **実績（4 システム対比）**: **インライン + 欄特定が優位**。トースト逐次型は文言が的確でも
  「どの欄か」を目視で探す一手間が乗る
- **重量級の派生所見**: 「**解消可能なエラーと解消不能なエラーが同じ見た目で並んでいないか**」。
  入力不可の欄が必須バリデーション対象になっている自己矛盾は、同じ赤枠・同じ文言なのに
  操作では絶対に解消できず、**130 手ギブアップ**の構造的な詰みになった
- **派生文型 = 重複エラー計測**: 「既存の番号 ◯◯ で登録を試みて。エラーになったら画面が
  『なぜダメか・どうすればよいか』を教えてくれたかを報告」— エラー案内の「理由だけ / 対処まで」を
  単離計測できる（**修正前 77 手の迂回 → 修正後 43 手**の実績）

## M. 境界値・入力事故 (boundary-input) — 高収穫

- **業務データに境界値を自然に埋め込む**（ゴール文に UI 用語を出さない）:
  存在しない日付「納期 2 月 30 日」・大数量 12,000 個・「無償（0 円）で提供」等。
  指示された事故値をペルソナがどう入力し、システムがどう受けるかを DB 裏取りで判定する
- **実績 3 件**: ①期間欄に壊れた日付を入れて 500 エラー（自然発生）②別画面の日付欄は
  2/30 を入口で防御 — ペルソナは 2/28 に丸めた上で**備考に「要確認」とメモを残した**
  （良い適応の記録）③0 円受注がノーガードで通ることを検出
- **注意**: 急ぎペルソナの二重送信は自然発生しなかった（2 波とも DB 重複ゼロ）。
  二重送信を測りたいなら L 系のように明示設計が要る

## N. 並行編集 (concurrent-edit) — 部分検証・要注意

- 2 ペルソナ × 同一 DB × 別ブラウザで、同一レコードの別フィールドを同時期に編集させる
- **学び（実測）**: **自由走行では編集タイミングが直列化し、真の衝突が再現しない**
  （後手がフォームを開くのは先手の保存後 → 最新値を取り込んで両立してしまう）。
  保護機構の不在（無音で上書き・編集中表示なし）の**観測はできる**が、
  後勝ち上書きの実証には「先行フォームをオーケストレータが開いたまま保持し、
  後手だけペルソナに走らせる」半構成シナリオが必要

## ペルソナ × モードのバリエーション

| モード | 測るもの |
|---|---|
| **blind**（既定） | 素の直感性 |
| **manual-guided**（通読） | マニュアルの網羅性・記載と実機のズレ |
| **reference-guided**（詰まったら引く） | マニュアルの**検索性**（目次から該当章に辿り着けるか）。実ユーザーの使い方に最も近い |

## ゴール設計の落とし穴（すべて実測）

- **UI 用語を書いた時点で失格**。ボタン名・画面名・タブ名・モーダルという語がゴール文に
  入っていないか、送信前に自己検査する（語そのものが操作の答えを教えてしまう）
- **固有名詞はデータと事前突合する**。ゴール文中の取引先名・案件名・番号が対象 DB に実在し、
  表記が一致することを確認する（初回実走で呼称の不一致がノイズ的な詰まりを 2 件生んだ）。
  呼称ゆれへの耐性を測りたい場合のみ、意図を明記した上で許可する
- **write 系ゴールを同一 DB で連続実行すると、前ペルソナの痕跡が見える** → ペルソナ間で DB 復元
- **正解キーは復元後に採る**（復元でデータが変わると正解も変わる。実走で、前ペルソナの登録を
  復元で消した結果、正解が 8 件 → 7 件に変化した）
- **曖昧語の正解キーは全候補フィールドで採る**。「直近の受注日」は受注日 / 注文日 / 納期の
  どれにも解釈できる。MAX を全候補で採り、ゴール文で「**画面のどの項目の日付か**を添えて」と
  指定する（実走で「1 日ズレの誤答」に見えた回答が、実は別フィールドの正しい読み取りだった）
- **数字だけで完結するゴールは、日本語入力の例外を発生させない**（数量・日付は 1 文字ずつ
  打てるため）。日本語入力の問題も見たいなら、文字列入力を含むゴールを混ぜる
