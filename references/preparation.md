# 走らせる前の準備

ペルソナを起動する前にやること。**ここを飛ばすと、測定結果が測定ミスなのか
本当の UX 問題なのか判別できなくなる。**

---

## 1. 偵察（対象システムを自分が把握する）

ペルソナには何も教えないが、**オーケストレータ（この作業をする人 or AI）は
全部知っている必要がある**。
ゴールが実行不可能だったり、正解が採れなかったりすると走行が丸ごと無駄になる。

調べておくこと:

- **画面地図** — URL / View / テンプレートの対応表、メニュー構造の階層
- **権限ゲート** — 自動ログインするユーザーが、目的の画面にアクセスできる権限を持っているか
  （**ゴールの画面が権限ゲートの内側だと走行が詰む**）
- **データ在庫** — 主要テーブルの行数（**空テーブル = ゴールにできない領域**）、
  ゴール素材になる実データ（取引先名・品番を数件）、採番体系と未使用の番号
- **ガードの有無** — 参照されているデータの削除ガード、重複チェック
  （エラー系ゴールが成立する条件）

### 正解キーの設計（最重要）

ペルソナの「達成しました」は信用しない設計なので、**正解を先に確定しておく**必要がある。

- **「UI に露出している実数」から問いを作る**。DB にしかない値で問いを作ると、
  ペルソナが正しく操作しても答えられない
- **キーのカラムは「画面の表示列の正本」を実装で確認してから選ぶ**。カラム名の字面一致に
  飛びつかない（実測: 一覧の「所有者」列の正本は `created_by` で、`owner_id` は別概念だった。
  `owner_id` を見て「DB が変わっていない」と誤警報した）
- **正解キーの採取は、DB 復元の後・ペルソナ起動の直前に行う**

### 正解キーを書いた台帳の置き場所（実害あり）

**ペルソナの成果物ディレクトリ（ログ・スクショの出力先）に、正解を書いたファイルを置かない。**

実測: 作業ディレクトリの `README` を「自然な行動として」読んだペルソナが、
走行冒頭で正解と導線を全て知ってしまい、走行を破棄した。

`agents/ux-blind-tester.md` の許可リストは `Read` を含む（**ペルソナは自分が撮った
スクリーンショットを `Read` して画面を見る**ので必須。加えてマニュアル監査モードでも使う）。
台帳は**到達圏外のディレクトリ**に置くこと。

### 🚨 起動ディレクトリに注意（封印の最大の穴）

**`claude --agent` で起動したセッションにも、`CLAUDE.md` / `AGENTS.md` は自動でロードされます。**

- **プロジェクトレベル**（起動した作業ディレクトリの `./CLAUDE.md`）
- **ユーザーレベル**（`~/.claude/CLAUDE.md`）は **作業ディレクトリに関係なく常に載る**

つまり、対象システムの実装規約・画面構成・命名規則を `CLAUDE.md` に書いている開発者
（＝このツールを使いたい人そのもの）が対象リポジトリの中で起動すると、
**ペルソナは初見ではなくなります**。許可リストによる封印は「ファイルを読む経路」を
塞いでいるだけで、「システムプロンプトに最初から入っている経路」は塞げません。

対処:

- **対象システムのリポジトリ内で起動しない**。`CLAUDE.md` / `AGENTS.md` の無い
  専用の空ディレクトリ（走行ログの置き場など）から起動する
- **`~/.claude/CLAUDE.md` に対象システムの記述が含まれていないか、走行前に確認する**。
  含まれるなら、一時的に退避するか `--settings` で別プロファイルを渡す
- 走行後の監査に「**コンテキスト由来の知識混入**」を 1 項目加える
  （ペルソナが、画面に出ていない内部用語やモデル名を使っていないか）

## 2. 環境の準備

### 本番では絶対に走らせない

ペルソナは削除も一括更新も遠慮なく実行する。**壊してよいコピー**を用意する。

さらに、**本番データベースへの書き込みを物理的に止めておく**ことを勧める。
テスト環境のサーバーが落ちると、ペルソナは自己復旧を試みて**本番サーバーを起動して
しまう危険がある**。`agents/ux-blind-tester.md` の「障害時プロトコル」はその対策だが、
契約は最後の防壁であって最初の防壁ではない。

### 外部への送信を止める

テスト環境から外に出ていくものを塞ぐ。特に:

- **エラー監視サービス（Sentry 等）の送信先を空にする** — ペルソナが意図的に起こした
  500 エラーが本番の監視に飛び込む。開発用の分岐に本番の送信先がハードコードされている
  ことは珍しくない。**分岐の実効判定に賭けず、設定ファイル内の全出現を確認すること**
- **デバッグツールバーを消す** — 画面に写り込んで、ペルソナが「これは何だろう」と
  操作対象にしてしまう
- **メール送信・外部 API・ファイル変換プロセスの起動**を止める

### トーストの表示時間を延ばす（vision 特有の対策）

**自動で消える通知（既定 3〜5 秒）は、スクリーンショットの撮影間隔と競合する。**

実測で「トーストは確かに出ているのに、ペルソナのスクショに写らない」という偽陽性が
繰り返し発生した。テスト環境限定で表示時間を 60 秒程度に延ばしておくと、
**「写っていない = 発火していない」と一意に切り分けられる**。

- これは**逸脱**である（実際の表示時間での知覚テストではなくなる）ことを記録に残す
- 重要な情報をトーストだけに載せない、という設計原則は別途守る
- 延長した後、実際に通知を 1 回発火させて 6 秒後に生存しているか確認する
  （設定ファイルを書き換えただけでは、別経路の実装が素通しになることがある）

### サーバーの同一性を確認する

起動後、ペルソナを投入する**前に**必ず確認する。

1. 対象ポートを LISTEN しているプロセスが、自分が起動したサーバーであること
2. トップページのタイトルが対象システムのものであること
3. 正解キーを、**そのサーバーが実際に参照している DB** から採っていること

実測: 起動スクリプトが「起動しました」と表示しつつポート競合で死んでおり、
HTTP 200 を返していたのは**別システムの常駐サーバーだった**。
ペルソナ 1 体が丸ごと別のシステムを監査してギブアップした。

**HTTP 200 が返るだけのスモークテストは、他人のサーバーでも通る。**

### 認証をどう通すか（業務システムなら必ず要る）

設定ファイルの `--isolated` は**毎回まっさらな状態**（Cookie 無し）でブラウザを起動する。
ログインが必要なシステムでは、何もしないとペルソナはログイン画面に着地して、
ID もパスワードも持たないまま「進めない」と報告して終わる。

選択肢は 3 つ。

| 方法 | 内容 | 副作用 |
|---|---|---|
| **(a) テスト環境限定の自動ログイン**（推奨） | 開発環境だけログインを省略する仕組みを入れる | ログイン画面を監査対象にできなくなる。**逸脱として記録する** |
| **(b) ゴール文で資格情報を渡す** | 「ID は ◯◯、パスワードは ◯◯ です」を業務前提として書く | **ログイン操作自体が観測対象になる**（これはこれで価値がある）。資格情報は UI 用語ではないので封印違反にはならない |
| **(c) ログイン済み状態を注入する** | playwright の `--storage-state` でセッションを渡す | 状態ファイルの管理が要る |

**(b) を選ぶなら、ゴール文に資格情報の行を足す**のを忘れないこと。

### 自動リロードを切る

開発サーバーのファイル監視付き自動リロードは、走行中の環境再構築時に落ちる原因になる。

### 🚨 DOM の自動保存を消し続ける（封印の穴・実測で確認）

**playwright MCP は、スクリーンショットを撮るたびに DOM のアクセシビリティツリーを
`--output-dir` へ `page-<日時>.yml` として自動保存する。** しかも
`browser_take_screenshot` の**応答に `### Snapshot - [Snapshot](page-….yml)` という
リンクを付けて提示してくる**。

ペルソナは `Read` を持っている（自分のスクリーンショットを見るために必要）ので、
**このリンクを開けば DOM が丸見えになる**。許可リストから `browser_snapshot` を外しても、
同じ情報が別経路で届いているということ。

```yaml
# page-<日時>.yml の中身（形式のイメージ）
- link "（サービス名）ホーム" [ref=e5] [cursor=pointer]:
    - /url: /
- button "（メニュー項目）" [ref=e30]
- textbox "（入力欄のラベル）" [ref=e42]
```

**対処は走行中に消し続けること。** 出力先を分けるのでは解決しない
（ペルソナは自分のスクリーンショットを読むので、同じディレクトリを知っている必要がある）。

```bash
# 走行中ずっと回しておく（30 分で自動終了）
end=$((SECONDS+1800))
while [ $SECONDS -lt $end ]; do
  rm -f /path/to/run/page-*.yml 2>/dev/null
  sleep 1
done
```

実測: この watchdog を回した走行では YAML の残存 **0 件**、ペルソナの非スクリーンショット
`Read` も **0 件**で、封印が保たれた。回さなかった走行では YAML が残っており、
**ペルソナが読まなかったのは契約を守ったからであって、読めなかったからではない**。

## 3. 複数体を走らせる場合

### ブラウザは必ず分ける

座標クリックは「アクティブなページ」に効く。**1 つのブラウザを複数のペルソナで共有すると、
別のペルソナの操作が割り込んで互いの画面を叩く。**タブ分割でも解決しない。
ブラウザ（MCP プロセス）ごと分けるのが唯一の方法。

### データも分ける

ペルソナ A の操作でペルソナ B の初見状態が汚れないようにする。選択肢は 2 つ:

- **直列で走らせ、ペルソナ間で DB を復元する**（省コスト。既定）
- **システムをまるごと複製して、ペルソナごとに独立インスタンスを渡す**
  （macOS の APFS なら `cp -Rc` によるコピーオンライトで一瞬・ディスクほぼ 0）。
  この方式なら DB 復元が不要で、破壊的な操作も無害になる

複製する場合、**コード・DB・アップロードファイルを全部含める**こと。
DB の行がファイルを参照しているので、ファイルを含めないと壊れた表示になる。

### 監視する

ペルソナの契約は「サーバーが落ちたら**自力で復旧せず中断報告する**」になっている。
つまり**復旧はオーケストレータの責任**。走行中はサーバーの生存を監視し、
落ちたら再起動する。ペルソナに自己復旧の動機を与えないことが本質。

```
[ ] DOM の自動保存 (page-*.yml) を消す watchdog を起動した

```
